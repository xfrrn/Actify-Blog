个人博客的维护动作可以很简单：新增一份文件，写好标题和正文，预览后发布。文章列表、目录和订阅应该跟着内容更新，否则每写一篇文章，就要额外记住几个容易遗漏的地方。

这个网站基于 Magic UI Portfolio 模板修改，文章放在 `content/blog/`，作品放在 `content/projects/`。下面记录的是当前仓库已经使用的内容组织方式，相关实现可以在 [Actify-Blog 仓库](https://github.com/xfrrn/Actify-Blog) 中查看。

## 一篇文章，从一个文件开始

以一篇中文阅读笔记为例，文件可以叫 `reading-note.zh.mdx`：

```mdx title="content/blog/reading-note.zh.mdx"
---
title: "一篇阅读笔记"
description: "记录一个具体问题，以及目前理解到的地方。"
date: "2026-09-19"
language: zh
category: "学习记录"
tags: ["阅读"]
draft: true
---

## 这次的问题

在这里写正文。
```

文件头保存文章信息，正文从二级标题开始，页面会单独显示文章标题。文件名中的 `reading-note` 决定地址 `/blog/reading-note`，`.zh` 表示中文版本。

本站同时接收 `.md` 和 `.mdx` 文件，并统一经过 MDX 编译。普通文章用 Markdown 语法就够了；需要嵌入已经接入站点的组件时，再使用 MDX 的组件能力。

新文章先保留 `draft: true`，检查完内容后改为 `false`。这个字段在本站是明确的发布开关。

## 内容进入页面之前，先经过校验

`content-collections.ts` 负责读取文章，并校验标题、摘要、日期、标签等字段。新文章使用 `date` 和 `description`；配置也保留了旧字段的兼容逻辑。

通过校验的公开文章会被编译，同时从正文生成目录和预计阅读时间。后续页面读取生成的数据，内容流转大致如下：

```text title="本站文章的数据流"
content/blog/*.md 或 *.mdx
  → 校验字段、解析文件名、编译公开正文
  → .content-collections/ 生成数据
  → 按语言选择版本、过滤草稿、排序
  → 首页 / 博客列表 / 文章页 / RSS / Sitemap
```

这让错误尽量在构建阶段暴露。例如，文件后缀写着 `.zh`，文件头却声明 `language: en`，就会被拒绝。同一个地址的同一种语言也不能同时存在 `.md` 和 `.mdx` 两份文件。

## 两种语言，共用一个文章地址

给刚才的文章增加英文版本，只需要新增同名文件：

```text
content/blog/reading-note.zh.mdx
content/blog/reading-note.en.mdx
```

两份文件共用 `/blog/reading-note`，标题、摘要、正文和目录各自维护。语言切换会选择一整份文章，避免出现英文标题配中文正文的情况。

当前选择规则是：先过滤草稿，再为每个文章地址选择访客偏好的语言；没有对应的公开版本，就显示另一种语言，并在页面提示。具体行为如下：

| 已有内容 | 中文界面 | 英文界面 |
| --- | --- | --- |
| 中文和英文都公开 | 中文版 | 英文版 |
| 中文公开，英文为草稿 | 中文版 | 中文版，并提示原文语言 |
| 只有公开的英文版 | 英文版，并提示原文语言 | 英文版 |
| 两种语言都是草稿 | 不展示 | 不展示 |

因此，一篇文章有两份译文时，列表仍只计为一篇。RSS 和站点地图同样按地址去重，公开订阅优先选择英文，没有英文则使用中文。

两份译文最好使用相同的日期和分类。当前页面会按选中的版本排序和筛选，如果两个版本填写不同分类，切换语言时文章可能出现在不同分组中。

## 草稿状态要沿着整条流程生效

只从列表里隐藏草稿还不够。读者可能直接打开文章地址，也可能从订阅或站点地图发现它。

本站公开查询统一从过滤后的文章集合读取：首页最新文章、博客分类计数、文章路由、RSS 和站点地图都沿用这个结果。只有草稿的文章没有公开详情页；某篇文章仅英文译文为草稿时，仍可以打开已公开的中文原文。

这种做法减少了每个页面各写一遍判断的机会。不过，草稿开关只控制网站展示。如果代码仓库是公开的，提交进去的草稿源文件仍然可以被查看。

## 语言切换还有一个明确的边界

本站用 Cookie 记录语言偏好，同一地址在服务端选择对应内容。这个方式满足当前的阅读切换需求，但中英文没有各自独立的 URL。

如果之后要让两种语言分别参与搜索发现，应重新考虑语言路径，例如 `/zh/blog/reading-note` 与 `/en/blog/reading-note`，并配置相应的语言标记。Google 对多语言网站建议采用独立语言 URL，而依赖 Cookie 切换的所有版本不一定都能被抓取。见 [Google 多语言网站指南](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites)。

这个区别也记录在 [小工具网站的 SEO 起步笔记](/blog/seo-basics-for-a-small-tool-site) 中，方便以后调整路由时一起检查。

## 发布一篇文章，需要检查什么

内容写完后，先确认标题能说明文章解决的问题，摘要与正文一致，代码和链接可以使用。然后在本地运行现有检查：

```sh title="在本站仓库中检查文章"
npm run typecheck
npm run test:content
npm run build
```

`typecheck` 会生成内容数据，内容检查会核对编译结果、目录和语言配对规则。构建通过后，还要打开文章看看长标题、代码块和表格，尤其是窄屏下的表现。

文章文件就是日常维护入口。只有当多人编辑、在线审核或其他明确需求出现时，才有必要重新评估是否引入内容管理后台。
